# Free-Tier Staging Environment (MID-625)

Board decision (MID-71, 2026-10-06): **no AWS, no paid services.** Staging runs on 100% free tiers. No ECS, no `terraform apply`.

## Stack

| Layer    | Provider            | Plan | Config in repo                                   |
| -------- | ------------------- | ---- | ------------------------------------------------ |
| API      | Render              | free | `render.staging-free.yaml` (repo root)           |
| Postgres | Neon                | free | connection string supplied as env var/secret     |
| Frontend | Vercel              | free | `prequal-platform/vercel.json`                   |

## One-time setup (board actions)

1. **Neon** — create a free account at neon.tech, create project `prequal-staging`, copy the **pooled** connection string (native format `postgresql://user:pass@host/db?sslmode=require`).
2. **Render** — create a free account, New + -> Blueprint -> connect `siumsamuel2-bot/prequal-platform`, accept the default `render.yaml` path (the repo-root file IS the staging-free blueprint). The blueprint pins `branch: develop`: the service **MUST** track `develop` — the same branch the CI `deploy-staging` job targets. If the service already exists and tracks another branch, change it in the Render dashboard (Service -> Settings -> Branch -> `develop`) and redeploy. When prompted for `DATABASE_URL`, **paste the Neon connection string exactly as Neon gives it** (`postgresql://user:pass@host/db?sslmode=require`). No hand-editing is needed: the app normalizes the URL to the async `asyncpg` driver and translates `sslmode=require` -> `ssl=require`, and `alembic/env.py` normalizes the same URL to `psycopg2` with `sslmode=require` (MID-653). `SECRET_KEY` is auto-generated by the blueprint.
3. **Vercel** — create a free account, Add New Project -> import the repo, set **Root Directory** to `prequal-platform` (the repo root also contains CI files; vercel.json inside `prequal-platform/` configures the Vite build). Set env var `VITE_API_URL` to the Render API URL (e.g. `https://prequal-staging-api.onrender.com`).
4. **CORS** — update the Render service env var `ALLOWED_ORIGINS` with the Vercel staging URL (e.g. `https://prequal-staging.vercel.app`) and redeploy.

## Migrations

Applied automatically on Render service start (`startCommand` runs `alembic upgrade head` before uvicorn). `alembic/env.py` reads `DATABASE_URL` from the environment, so both the Render service and manual runs target the real database (no localhost fallback when the env var is set).

One `DATABASE_URL` works for **both** drivers as-is (MID-653). `app/database.py` normalizes it onto `asyncpg` (and maps `sslmode=` -> `ssl=`), and `alembic/env.py` normalizes it onto sync `psycopg2` (and maps `ssl=` -> `sslmode=`). Do not maintain two URL strings.

- **Migrations (sync driver, psycopg2):** the native Neon string works unchanged:

  ```
  cd prequal-platform
  DATABASE_URL="postgresql://user:pass@host/db?sslmode=require" alembic upgrade head
  ```

  (`+asyncpg://` and `+psycopg://` URLs are also accepted; `alembic/env.py` rewrites any Postgres scheme to `+psycopg2` automatically.)

- **Render app secret (async driver, asyncpg):** paste the same string. The app's `create_async_engine` path uses `asyncpg` and accepts either `ssl=` or `sslmode=`; normalization is automatic.

## Free-tier limits and cold starts

- **Render free web service:** 512 MB RAM, shared CPU, spins down after ~15 min of inactivity; first request after spin-down takes ~30-60 s (cold start). Cold starts are acceptable for staging/pilot validation.
- **Neon free:** ~0.5 GB storage, compute scales to zero; cold start ~<1 s on resume.
- **Vercel free (Hobby):** 100 GB bandwidth/month, serverless function limits do not apply (static frontend).
- **GitHub Actions:** free for this repo (standard minutes).

## Frontend fallback host (MID-685, insurance path)

If the board's Vercel import keeps failing, the root `render.yaml` blueprint now also defines a **Render Static Site** for the SPA (`prequal-staging-frontend`, free tier): same Vite build (`npm ci && npm run build`, publish `dist`, Node 18 to match CI), plus two rewrite rules:

- `/api/*` -> `https://prequal-staging-api.onrender.com/api/*` (server-side proxy - the SPA's same-origin default, so no `VITE_API_URL` and **no CORS change**)
- `/*` -> `/index.html` (SPA client-side routing fallback; must stay second)

Board click-path (fallback only - the Vercel deploy stays primary; do not remove it):

1. Render dashboard -> open the existing `prequal-staging` Blueprint -> **Apply Changes** (Render detects the new `prequal-staging-frontend` static service from `render.yaml`). Alternatively: New + -> Static Site -> connect the repo, set Root Directory `prequal-platform`, build `npm ci && npm run build`, publish `dist`, add the two rewrite rules above in that order.
2. Wait for the build (~2-3 min), then open `https://prequal-staging-frontend.onrender.com` and verify: SPA loads, register/login works, dashboard data loads (API proxied same-origin).
3. Realtime note: WebSockets are not proxied by the static CDN; the app automatically falls back to polling (`useRealtimeConnection`).

If the proxy path ever misbehaves, plan B: set build env `VITE_API_URL=https://prequal-staging-api.onrender.com/api` and append `https://prequal-staging-frontend.onrender.com` to the API service's `ALLOWED_ORIGINS`, then redeploy both.

## Notes

- **Deploy branch is `develop` — always.** `master`/`main` are NOT the deploy branch. Both `render.yaml` and `render.staging-free.yaml` pin `branch: develop` (MID-678), matching the CI `deploy-staging` job; a service left on the repo default branch builds stale code — this caused the migration-016 staging outage (MID-675).
- Root `render.yaml` (repo root discovery) **is the staging-free blueprint** — the board can accept Render's default path. The paid production config lives at `prequal-platform/render.yaml` (Render DB/Redis) and must NOT be applied for staging; `render.staging-free.yaml` is an identical copy kept for "Apply from file".
- No secrets are committed to the repo; all credentials are provider-side env vars.

## Automated provisioning (MID-648, alternative path)

`.github/workflows/provision-staging.yml` provisions the same free stack via provider APIs in one manual dispatch (Actions tab -> Provision Staging (free tier) -> Run workflow). It is an **alternative** to the manual dashboard steps above — the dashboard path stays valid.

- **Prerequisite (board):** store `RENDER_API_KEY`, `NEON_API_KEY`, `VERCEL_TOKEN` as repo secrets (Settings -> Secrets and variables -> Actions). Without tokens the workflow is a safe no-op (CI stays green; the summary job explains what is missing).
- **What it does:** Neon — create-or-reuse free project `prequal-staging` and resolve the pooled connection URI; Render — create-or-reuse web service `prequal-staging-api` (free plan, mirrors the root `render.yaml` blueprint 1:1: runtime python, rootDir `prequal-platform`, same build/start commands and env vars), sets `DATABASE_URL` (converted to `?ssl=require` for asyncpg), deploys and waits for live; Vercel — create-or-reuse project with `VITE_API_URL` set to the Render URL, deploys and waits READY; CORS — updates Render `ALLOWED_ORIGINS` with the Vercel URL and redeploys. The Neon DATABASE_URL never leaves the Render job; only public URLs appear in the run summary.
- **Note:** Render's API cannot create Blueprints (dashboard-only), so the workflow creates the service directly with the same definition as `render.yaml`. Render also requires its GitHub app installed on the repo (one-time) for the Vercel/Render git-based deploys. When dispatching, set the `render_branch` input to `develop` — the default is still `task/mid-18`, and a service tracking any other branch will deploy stale code (MID-678).
- Re-runnable: provider resources are reused by name; re-running re-syncs env vars and redeploys.
